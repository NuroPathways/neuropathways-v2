# 3. IMPLEMENT THE LEGACY FAMILY-SCOPED BRIDGE

## This is the first major unfinished feature.

I explicitly approve:

**YES — Add a family-scoped bridge for legacy username-and-access-code family logins.**

The existing username/access-code flow should continue working.

Parents must NOT have to create a second account simply to access the newer parent interface.

Do not copy existing clinical records into newer parent tables just to make the UI work.

## Required authentication behavior

When a legacy username-and-access-code user logs in:

1. Validate the credentials using the existing secure login process.
2. Validate the resulting server-backed session.
3. Identify the child account associated with that login.
4. Retrieve its family relationship.
5. Determine the family account type from trusted server-side data.
6. Check whether this is a family/caregiver account or an individual self-managed client account.
7. If it is a family/caregiver account, create an authorized family-scoped parent-session context.
8. Retrieve only the children that the authenticated session is permitted to access.
9. Load the unified parent application.
10. Preserve the existing username/access-code authentication method.

If the account is an individual self-managed client, keep that user in the appropriate client experience.

If the account type is unclear, do not guess or automatically grant family access. Use a safe fallback and surface the account-classification issue for correction.

## Family authorization

The bridge must enforce:

- verified family membership
- the applicable clinician/tenant boundary
- valid session credentials
- session expiration
- child-level access
- record-level permissions

Only family members and children authorized for that session may be returned.

Do not use family IDs, clinician IDs, or child IDs supplied by the frontend as proof of authorization.

Do not grant access to every child who shares a clinician.

Do not grant access to other families under the same clinician.

Do not rely on client-side routing for security.

## Important distinction

A legacy child-scoped session is NOT automatically a parent account.

The bridge must establish an appropriately restricted family capability on the server.

It must not:

- forge a parent-account cookie
- convert a child session into a clinician session
- impersonate another user
- grant clinician permissions
- copy clinical records unnecessarily
- expose sibling records without authorization

## Session persistence

When a legacy family account refreshes the app:

- preserve the valid authenticated session
- restore the unified parent experience
- restore the selected child if still authorized
- prevent redirecting into the older dashboard

When a session expires, use the existing reauthentication process.

Do not silently substitute another stored account session.
